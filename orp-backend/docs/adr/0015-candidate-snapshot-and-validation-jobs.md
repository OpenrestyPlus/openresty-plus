# ADR-0015：配置候选快照与持久化校验任务

## 状态

已接受（目标架构）；当前实现尚未满足本 ADR，见“实现状态”。

## 决策

- 候选是独立、不可变的 MySQL 记录，保存中心、创建者、配置快照及摘要、Diff 基线版本/摘要、精确目标节点快照、生成时间和归档状态。候选生成和读取草稿使用同一个 MySQL `REPEATABLE READ` 一致性事务；若任一输入读取失败则回滚，不写入候选。
- 候选生成事务内同时写入首个校验尝试及逐节点待验证结果。Diff 基于冻结快照立即计算；每次重试写新尝试，不覆盖历史结果。
- MySQL 是候选、调度和审计证据唯一权威。验证任务与逐节点状态持久化到 MySQL；控制面后台 worker 使用短事务领取工作、租约与超时回收，节点校验在事务外执行。Redis 不可用不影响任务正确性。
- 每中心配置最大在途校验数。调度器在有待处理任务的候选之间轮转，每轮每个候选至多派发一个节点任务；候选配置只能下调自己的并发，不得突破中心上限。
- 任一目标校验失败后暂停该尝试尚未派发的节点；在途任务完成并落库后，等待具备中心配置编辑权限的操作者继续或停止。进程重启后租约过期任务标为结果未知，不自动重试；操作者可逐节点重试。
- 节点操作只允许部署提供的固定暂存/校验脚本和参数白名单。上传制品、在非活动目录运行目标节点 `nginx -t`、回收暂存物是后续需实现并集成测试的节点适配器；不得调用会激活配置、Control API reload 或 restart 的部署脚本。
- 首期候选只归档/取消归档，不硬删除；创建、重试、继续/停止、归档操作及逐节点结果记入审计。

## 后果

- MySQL 行锁和租约提供多控制面实例间的唯一任务领取与故障恢复，不以进程内 goroutine 状态作为事实源。
- 首次实现必须补齐确定性配置渲染及安全的非活动暂存校验链路；在此之前不得把“候选生成成功”宣称为“目标校验通过”。
- 本 ADR 只覆盖候选准备，不启用发布、激活、reload、restart、canary 或独立审批。

## 实现状态（2026-10-08）

当前 Go 控制面采用另一条已交付的本地 Compose 流程：`POST /api/orp/publish/precheck` 在请求中同步冻结候选、逐节点执行 `nginx -t` 并保存 Diff/校验结果；`POST /api/orp/publish` 随后可创建并执行本地节点发布批次。候选与结果表由 V34/V35 创建，但尚无异步校验尝试、租约、公平调度、候选列表/归档/重试/继续接口，也没有中心级候选并发控制。此流程只允许三个固定 Docker Compose 节点。

因此，本 ADR 描述的目标能力不应被视为当前已实现；它与 Compose MVP 的实际发布能力是不同阶段/范围。任何文档描述当前服务时应以 `docs/frontend-backend-migration-status.md` 的实现证据为准。
